# 已知问题与标注含义

本仓库发布的是已有 MassSpecGym MAGMa 数据生成代码的便携化副本。本次仅整理导入路径、依赖和运行说明，**没有修正碎裂算法、匹配规则或历史数据标签**。下列问题适用于 RA 理解和检查输出；成功运行、匹配率高均不等于结构标注已经验证正确。

主要代码位置：

- `fragments/magma/op/Magma4MassSpecGYm.py`：输入解析、谱峰匹配、JSON 导出和 CSV 批处理。
- `fragments/magma/op/fragmentation_op_v8.py`：分子处理、片段生成及位图表示。
- `fragments/magma/chem_utils.py`：互变异构体规范化和 adduct 质量表。

## 1. 默认分子变换可能导致导出的原子索引与 SMILES 不一致

`FragmentEngine.__init__` 默认执行以下流程：

```text
输入 SMILES → RDKit molecule → InChI → 互变异构体规范化
           → SMILES → 重新解析得到引擎使用的 molecule
```

片段 `atom_indices`、断键 `bond_indices` 和 `bond_atom_pairs` 都来自引擎最后使用的 molecule。`build_annotated_data` 的顶层 `smiles` 却仍写入原始输入字符串。原子排序改变时，直接按导出的 SMILES 重新建图再使用这些索引，会选中错误原子或键；互变异构体改变时，局部键型和附氢还可能不同。

本次对历史验证集的 **单个样本 `spec_id=143`** 做了检查：

- 该样本有 9 个匹配峰。
- 按导出 SMILES 的原子顺序解释索引，7 个匹配片段的重元素组成与记录的 `formula` 不一致。
- 按生成器的规范化分子图解释相同索引，9 个片段的重元素组成全部一致。

这验证了该样本存在索引坐标不一致，**不能据此推算整个验证集或全部历史数据的受影响比例**。这里比较的是重元素组成，未将氢迁移与离子质量等同于完整结构验证。

`--no-canonicalize` 会跳过 InChI/互变异构体规范化及后续 SMILES 重解析，直接使用 RDKit 从输入 SMILES 解析出的图。它能够避免上述默认变换引入的重编号，但含义不只是“输入已经是 canonical SMILES 所以省一点时间”：canonical SMILES 与 canonical tautomer 不是同一个保证。切换该选项也会改变算法实际处理的分子图、附氢以及候选片段，不能把新旧结果直接视为完全等价。

历史文件没有保存足以可靠确认所有生成参数的完整运行配置。已有输出需要结合原运行命令和样本检查判断，不能仅凭文件存在推定采用了哪种模式。本次发布未给历史数据重映射索引。

## 2. 碎裂路径是算法生成的候选标签

`tree_depth` 表示片段最早被算法发现时经历的扩展层数。一次扩展是删除一个图原子，并保留所得连通分量之一；它不直接等于实验的 MSn 级数、真实反应步数或切断的化学键数。

同一原子集合可能由多条父路径到达。引擎把这些父关系保存在 `parent_hashes`，但 `build_fragment_lineage` 只沿第一个父片回溯，随后把这一条路径写入 `lineage_root_to_fragment` 和 `autoregressive_targets`。因此这些路径是生成顺序选出的一条候选解释，不能作为经过实验验证的唯一路径。

`match_peaks` 先选质量误差最小的候选，仅在误差完全相等时再用碎裂分数打破平局。一个峰导出的最佳匹配不意味着其他同质量或近质量结构已被实验排除。训练或评估时应明确标注为算法生成的监督信息。

## 3. Adduct 和电荷支持范围有限

`match_peaks` 用 `common.ion2mass.get(adduct, common.ion2mass["[M+H]+"])` 查询质量偏移。因此表外 adduct、拼写差异以及缺失值可能静默使用 `[M+H]+` 的质量，而输出仍保留原 adduct 字段。

当前实现只从观测 m/z 减去一个表中的质量偏移，没有按电荷数将 m/z 换算为中性质量。**多电荷前体不受正确支持**，例如 `[M+2H]2+` 不能按当前规则解释。运行前应核对输入 `prec_type` 的实际取值及数量，不能仅检查一个默认正离子示例。

另外，代码对每个 MS2 峰使用同一个前体 adduct 偏移。这是候选匹配模型的假设；对会失去加合基团的碎片是否适用，需要按具体谱图验证。

## 4. 位图原子数受到 int64 限制

引擎用原子集合位图表示片段，并在键位图、候选 ID 数组及 Numba 函数中使用 `np.int64`。**含 64 个及以上图原子的分子不受可靠支持**，会触及有符号整数的符号位或溢出。这里的图原子数取决于 RDKit 实际解析结果，不是把所有隐式氢加上后的总原子数。

当前没有完整的前置原子数检查。CSV 模式会捕获相关异常并记录 `success=False`，未必终止整个任务。RA 应检查汇总中的失败记录；不能把未导出的失败样本当作已经完成标注，也不能把这一原子上限以下的输入自动视为没有其他问题。

## 5. 生成任务没有断点续算，已有输出会被覆盖

`run_csv` 以 `open(annotated_output, 'w')` 打开输出，重新运行同一命令会覆盖已有文件。它不会读取已有样本 ID、跳过已完成样本或恢复上一次进度。

批量输出是一个含 `samples` 数组的整体 JSON，只在全部循环完成后写入结尾。进程被杀或机器中断时，已写入部分也可能不是完整可解析的 JSON。逐条写出不等于持久化的断点续算；当前还没有原子提交、完整性恢复或完成清单机制。

准备正式生成时，应给每次运行分配独立输出路径并保留输入和命令记录。若需要可恢复的分片生成，应先另行实现并验证该机制。本仓库当前版本没有承诺这一能力。网盘或对象存储的“传输续传”也不能恢复这里尚未生成完的标注。

## 6. 全候选图可能占据绝大多数输出空间

`build_annotated_data` 会导出所有生成片段的节点、原子索引、断键、父关系及图边，包括没有匹配到谱峰的候选；同时保留新旧两套峰标注字段。输出大小不只取决于谱峰数量。

本次检查的历史验证集单个样本 `spec_id=143` 有：

| 项目 | 实测值 |
| --- | ---: |
| 匹配峰 / 全部峰 | 9 / 9 |
| 候选图节点 | 10,055 |
| 候选图边 | 39,269 |
| 样本紧凑 JSON 序列化大小 | 6,268,742 字节 |
| 其中 `fragment_graph` 的序列化大小 | 6,243,345 字节，约 99.59% |

这些字节数来自本次对读取出的样本进行紧凑 JSON 序列化的统计，不是文件系统分配块大小。该例说明候选图可以远大于匹配峰记录；**它不是全数据集的平均值，也不能直接当作整个数据集的压缩比例**。

如果只使用最终匹配标签，可以考虑另行设计紧凑导出格式，但需保留重建真实父片差集所需的信息。直接删除图节点后让缺失父片回退到整分子，会改变训练标签含义。本次发布未裁剪图或重新生成数据。

## 7. 其他已确认的表示与覆盖限制

- **基础公式与氢迁移分别存储。** `get_form` 输出基础片段的公式；匹配质量可以再加 `h_shift × H`。使用者不能忽略 `h_shift` 后把 `formula` 直接当作匹配质量的最终化学式。
- **某些单原子分量会被遗漏。** `_extend_numba` 未在初始化时把种子原子置入返回位图。删除一个多邻接原子后，如果某个剩余分量只有单原子，该分量会返回零并被跳过；其他路径是否补回取决于分子结构和深度上限。本次未修复。
- **`max_broken_bonds` 不是总断键数的硬筛选条件。** 当前参数主要限制 H 迁移范围；生成循环没有在累计断键量超过该值时停止扩展。不要把默认值 6 描述成数据保证“最多切断 6 根键”。

## 下游历史提取器：不随本仓库发布

以下问题来自曾消费这些 JSON 的 `Spectrum_Prediction/data/extract_fragments.py`，**该提取器不随本仓库发布**。它们不应被误认为本仓库已修正的功能，也需要在复用已有训练数据时单独审计：

1. 提取器使用 `Chem.AddHs` 建立全原子图，而生成器的 `atom_indices` 来自未执行 `AddHs` 的图。新增氢不在候选索引中，可能被误当作丢失原子。
2. 提取器只从命中谱峰的片段建立父片索引；缺少中间父片时回退到整个分子，导致深层单步标签混入从根开始的累计丢失。
3. 提取器按深度对不同分支的丢失原子取并集，再从整分子扣除。不同候选碎片被混成一个累计删除序列，所得保留原子不等于原来的多碎片集合。
4. 通过 adduct 字符串任意位置是否包含 `-` 判定负离子，会把 `[M+H-H2O]+` 一类正离子判错；通过最大 MS2 峰填充 `precursor_mz`，也不能保证等于真实前体 m/z。

上述判断依据代码及一个已核验的历史样本。正式使用现有标签前，应按实际输入分布和原始谱图验证受影响范围；当前没有完成全数据集的正确性审计。
